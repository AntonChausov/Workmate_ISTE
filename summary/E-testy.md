# Категория E - Написание тестов

**Проект:** `amusementpark` + тестовое расширение `amusementpark.YAXUNIT`
**Поколения:** оригинал (июнь 2026) → версия 06.08.2026 → **версия 1.0.8 (03.10.2026)**
**Сравнение:** дословный повтор промптов более раннего прогона. В раунде
06.08.2026 - все четыре итерации, в раунде 1.0.8 - только E.1 (без
подготовки), два прогона

Разделы E.1-E.4 ниже описывают раунд 06.08.2026. Результат на версии
1.0.8 - в разделе «Версия 1.0.8», и он меняет главный вывод категории.

**Особенность этой категории:** единственная во всей проверке, где для
получения окончательного ответа пришлось не только анализировать текст, а
по-настоящему запускать тесты и итеративно передавать реальные ошибки
платформы без подсказок - статический анализ и самоотчеты неоднократно
оказывались недостаточными или неточными.

## E.1 - без контекста о фреймворке

**Промпт:**
```
Напиши тест YAXUnit для функции ДоляНакапливаемыхБаллов в модуле объекта
документа ПродажаБилета. Покрой основные сценарии и граничные случаи.
```

**Результат:** вместо немедленного (нерабочего) кода - два уточняющих
вопроса про доступ к неэкспортной функции и расположение модуля.
Инструмент честно признал границы возможностей при попытке переноса
модуля (не может самостоятельно изменить состав метаданных) - дал точную
пошаговую инструкцию вместо выдумывания успеха.

Реальный API использован без выдумок, но семь тестов из девяти падают
при запуске на одной и той же причине - попытка писать в регистр,
подчиненный регистратору, в обход самого регистратора. Один раунд правки
не устранил основную проблему. Итог: ни один тест из девяти не проходит
запуск.

**Оценка:** Корректность 1/3, Готовность 0/3, Стоимость 1/3 - **2/9 ❌**

## E.2 - минимальная наводка про фреймворк

**Промпт:**
```
Напиши тест YAXUnit для функции ДоляНакапливаемыхБаллов... Фреймворк
YAxUnit подключен в проекте как расширение amusementpark.YAXUNIT -
ориентируйся на его реальные модули...
```

**Результат:** три раунда реальных ошибок платформы, каждый раз верная
диагностика и исправление с первой попытки:
1. Ошибка вызова несуществующей комбинации методов → переключение на
   служебный модуль с добавлением экспорта к продуктовой функции
   (самостоятельное решение).
2. Конфликт ключевых полей из-за отсутствия изоляции тестовых данных →
   явное управление транзакцией добавлено ко всем тестам самостоятельно,
   без примера в тексте промпта.
3. Ошибка неопределенной переменной внутри вычисляемого выражения →
   верно диагностирована контекстная изоляция и самостоятельно принято
   решение об упрощении на прямой вызов метода. По пути файл был поврежден
   серией частичных правок - замечено и восстановлено самостоятельно,
   проверено валидатором.

Реальный запуск: восемь тестов из восьми проходят. Первый по-настоящему
зеленый результат категории.

**Оценка:** Корректность 3/3, Готовность 2/3, Стоимость 2/3 - **7/9 ✅**

## E.3 - авторский файл правил

**Промпт:** с приложенным файлом правил (стиль, минимизация тестов,
единый стиль построения тестовых данных, отношение к магическим числам,
использование вспомогательных предикатов и построителя тестовых
запросов).

**Результат:** самая долгая обработка во всей проверке - около 32 минут.
Три теста (сильная минимизация), логика безупречна при ручной проверке -
включая корректный выбор отдельной шкалы без открытого диапазона для
теста на выход за границы диапазона.

Реальный запуск: два теста из трех проходят. Один падает - из-за пустой
даты документа продажи, из-за чего платформенный механизм получения среза
последних записей не находит нужную шкалу. Раунд правки: диагноз верный
по направлению, но неполный, результат не изменился.

**Оценка:** Корректность 2/3, Готовность 1/3, Стоимость 1/3 - **4/9 ⚠️**
(качественно значительно лучше числового балла - логика содержательно
верна везде, нерешенная проблема узкая и техническая)

## E.4 - финальный файл правил + готовый каркас

**Промпт:** с приложенным финальным файлом правил (явный запрет
придумывать несуществующие методы, требование самопроверки ожидаемых
значений, отдельный раздел про регистры, подчиненные регистратору, пример
«плохо/хорошо» для явного управления транзакцией) + заранее подготовленный
каркас тестового модуля.

**Результат:** около 8 минут. Пять тестов, каждый с явной уникальной
датой - полностью обходит проблему пустой даты из E.3. Верно распознана
подчиненность регистра регистратору, верно выбран экономный способ
создания тестового документа без лишней записи. Логика при ручной
проверке безупречна.

Найдено (не в счет итога): у последнего теста нет явного управления
транзакцией, несмотря на выделенный финальный пункт самопроверки именно
для этого правила в файле - не повлияло на результат (тест ничего не
записывает), но показательный случай: явная инструкция «проверь это
перед сдачей» не гарантирует стопроцентного соблюдения.

Реальный запуск, с первого раза: пять тестов из пяти проходят.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**

## Наблюдения

### Положительные
- **Категория с самым большим ростом качества результата при добавлении
  подготовки.** Разница между отсутствием контекста и минимальной
  наводкой - от полного провала до рабочего результата.
- Три раунда реальной самокоррекции подряд в E.2 - все верные с первой
  попытки после получения текста настоящей ошибки платформы, без единой
  подсказки причины.
- Честное признание границ инструментария (E.1, перенос модуля) - вместо
  выдумывания успеха.
- Самостоятельное упрощение архитектуры (E.2) и самостоятельный выбор
  изолирующих дат (E.4) - инструмент не просто чинит конкретную ошибку, а
  иногда обобщает вывод на весь подход.
- E.4 дал лучший результат, чем можно было ожидать по опыту прежней
  версии - без необходимости в неудачной первой попытке.

### Настораживающие
- **Платформенная специфика регистров, подчиненных регистратору, -
  устойчивый, воспроизводимый пробел.** В E.1 (без контекста) - та же
  ошибка, что и в прежних экспериментах, и она не поддалась исправлению
  за два реальных раунда правки. Полностью обходится только при наличии
  подготовки (правил и/или наводки).
- Даже выделенный, недвусмысленный финальный пункт самопроверки не
  гарантирует стопроцентного соблюдения (E.4 - пропущено явное управление
  транзакцией у одного теста из пяти, несмотря на явную инструкцию именно
  проверить это перед сдачей).
- Диагноз может быть верным по направлению, но неполным (E.3 - «пустая
  дата документа продажи» была правильной, но не единственной причиной;
  повторная попытка с той же информацией не решила проблему).
- Внутренняя нестабильность агентного редактирования (E.2 - файл поврежден
  серией частичных правок) сохраняется как паттерн, но с надежной
  самокоррекцией каждый раз.

## Вывод для практики

По раунду 06.08.2026: написание тестов для функции с формализуемой
бизнес-логикой можно делегировать при наличии хотя бы минимальной
наводки о фреймворке - этого достаточно для рабочего результата после
реальной проверки и 2-3 раундов правки. С подробным, проверенным файлом
правил и подготовленным каркасом результат получается за один прогон.

**На версии 1.0.8 вывод меняется:** даже без какой-либо подготовки
Напарник в двух прогонах из двух написал тесты, которые прошли с первого
запуска (раздел ниже). Подготовка теперь влияет на стиль и
идиоматичность, а не на то, заработают ли тесты вообще.

## Версия 1.0.8 (03.10.2026) - E.1 без подготовки на новой модели

Тесты без подготовки три поколения подряд были самым слабым местом всей
карты: 1/9 в июне, 2/9 в августе. Это чисто модельное свойство
(выдуманный API фреймворка, регистр, подчиненный регистратору), поэтому
после заявленной смены модели в 1.0.8 я перепроверил именно эту
итерацию.

**Подготовка:** функция `ДоляНакапливаемыхБаллов` не экспортная, регистр
`АктуальнаяШкалаБонуснойПрограммы` подчинен регистратору, пользовательских
тестовых модулей нет ни в расширении, ни в конфигурации, память
Напарника пуста. Промпт дословно тот же, без правил и каркаса. Проверка -
реальный запуск тестов. Два прогона, каждый в новом чате, с откатом
изменений.

### Прогон 1 - 6 мин 31 с, 40% контекста

- Ни одного уточняющего вопроса (в августе было два), план из 6 шагов.
- Сам изучил исходники фреймворка и использовал **реальный API**:
  `ЮТТесты.ВТранзакции().ДобавитьТестовыйНабор(...)`,
  `ЮТест.ОжидаетЧто(...).Равно(...)`.
- Сам сделал функцию экспортной и прямо написал, что это единственная
  правка продуктового кода.
- **Сам создал общий модуль в составе метаданных расширения**, включая
  флаги компиляции.
- **Регистр, подчиненный регистратору, заполнил верно с первого раза** -
  через проведение документа `ШкалаБонуснойПрограммы`. Этого не смогло
  ни одно прошлое поколение без подготовки.
- 7 тестов: безлимит, границы диапазонов, срез по дате, выбор последней
  шкалы, «шкалы нет», сумма ниже минимальной границы.
- **Запуск: 7 из 7 зеленые с первого раза, без единой правки.**

### Прогон 2 - 6 мин 42 с, 70% контекста

- Впервые в исследовании Напарник **сам прочитал внешнюю документацию
  фреймворка** на сайте YAXUnit, а не только исходники.
- Стиль ближе к фреймворку: параметризованные тесты, тестовые данные
  через `ЮТТестовыеДанные`, очистка штатным механизмом.
- Интересный компромисс: написал fluent-конструктор, получил
  предупреждение EDT, попробовал подавить его комментарием, не
  получилось - и сам отказался от идиоматичного варианта ради «чистых»
  маркеров. Агент оптимизирует то, что можно измерить.
- **Запуск: 12 из 12 зеленые с первого раза, без единой правки.**

### Что это значит

Это самое сильное и воспроизводимое изменение раунда 1.0.8. Тезис трех
поколений «тесты без подготовки делегировать нельзя, регистры,
подчиненные регистратору, - устойчивый пробел» на новой модели
**опровергнут**.

Новые поведения: чтение внешней документации, самостоятельное создание
инфраструктуры (модуль в метаданных расширения), меньше вопросов.
Решения о продуктовом коде Напарник теперь принимает сам, но прозрачно
сообщает о них - такие попутные изменения обязательно смотреть на ревью.

На что смотреть: жестко зашитые даты и зависимость тестов от данных базы
повторились в обоих прогонах.
