# Категория F - Отладка и поиск ошибок по описанию симптома

**Проект:** `amusementpark`
**Версия инструмента:** 06.08.2026
**Сравнение:** дословный повтор промптов более раннего прогона, обе
подзадачи

## F.1 - доля оплаты бонусными баллами

**Промпт:**
```
При оформлении продажи билета клиенту, у которого накоплено много бонусных
баллов, иногда удается списать баллов больше, чем разрешено программой
лояльности - проверка максимальной доли оплаты баллами не срабатывает.
Найди, в чем причина, и предложи исправление.
```

**Поведение:** самостоятельный поиск (по метаданным и полнотекстовый) без
подсказки о месте - вышел на нужную процедуру и реквизит.

**Диагноз:** верный и полнее прежнего результата - определена причина
(устаревший реквизит, который в текущем коде всегда равен нулю) плюс
самостоятельно найдена и устранена побочная проблема - деление на ноль
при нулевой сумме продажи (в более ранней версии не рассматривалась).
Одна неточность формулировки: реквизит назван «заполняемым» в
миграционной процедуре, тогда как он там читается, а не заполняется -
сути диагноза не меняет.

**Исправление:** дословно совпадает с исправлением из прежней версии,
применено в коде, подтверждено проверкой модуля - новых ошибок нет.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**
(паритет с прежней версией, качественно выше)

## F.2 - ошибка заполнения при создании клиента

**Промпт:**
```
При создании нового клиента возникает ошибка «Поле "(Не использовать)
Телефон" не заполнено», и документ/карточку клиента невозможно сохранить,
даже если телефон в контактной информации указан. Найди причину и предложи
исправление.
```

**Диагноз:** верный, и впервые полностью явно назван механизм,
отсутствовавший в прежней версии, - точный порядок платформенных
событий (проверка заполнения на сервере происходит раньше события «перед
записью», реквизит еще пуст на момент проверки у любого нового клиента).

**Попытка применить исправление - главная находка эксперимента.** Обычный
способ редактирования отказал: «служебный файл метаданных, нельзя
редактировать напрямую» - как и в прежней версии. Но вместо капитуляции
Напарник самостоятельно запустил собственную агентную подзадачу через
JShell - консоль для выполнения кода прямо на объектной модели среды
разработки - нашел там нужный метод и константу для настройки
заполняемости реквизита, прошел через несколько неудачных попыток, подобрал
рабочий вариант, применил его и сам проверил результат (повторным чтением
файла и сравнением изменений).

**Проверка (независимо):** свойство заполняемости реквизита действительно
изменено на нужное значение; в проекте - только два замечания, не
связанных с этой правкой. Изменение реальное.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**

## Наблюдения

### Положительные
- Сильная сторона не деградировала. Оба диагноза получены без единой
  подсказки о месте проблемы - терминологический разрыв и незнание, где
  искать, по-прежнему компенсируются самостоятельным поиском.
- Впервые полностью назван механизм в F.2 - порядок платформенных
  событий, который в прежней версии был пропущен.
- Самостоятельная находка в F.1 - деление на ноль, не связанная с
  исходным тикетом, устранена попутно.
- Честный отказ штатного способа правки, но не капитуляция: в F.2 прямое
  редактирование корректно отказалось трогать служебный файл напрямую -
  но вместо инструкции для человека найден обходной путь.

### Настораживающие / важные
- **Прорыв в границе автономности - главная находка категории.** В более
  ранней версии правка объекта метаданных была недоступна в принципе
  (только инструкция для ручного применения). Сейчас через обходной
  технический путь файл метаданных отредактирован и сохранен,
  подтверждено независимой проверкой. Это прямо противоречит более раннему
  выводу «код - да, метаданные - нет» и требует его пересмотра - см.
  подробный разбор в файле категории H.
- **Внутренняя стоимость работы инструмента и стоимость для пользователя
  - разные величины.** Технически JShell-подзадача потребовала десятков
  шагов и нескольких тупиков (константа не находилась с первой попытки,
  была коллизия имени переменной) - но пользователь всего этого не увидел:
  один промпт, одно подтверждение. При оценке «стоимости получения» по
  методике намеренно считается пользовательский опыт, а не внутренние
  технические шаги - стоит явно держать это разделение в уме, иначе
  большое число внутренних шагов будет читаться как высокая цена для
  пользователя.
- Неточность формулировки механизма («заполняется» вместо «читается» для
  устаревшего реквизита) воспроизвелась и в F.1, не только в F.2 -
  устойчивый, но не критичный паттерн: вывод верный, слово для механизма
  - не всегда точное.

## Вывод для практики

Отладку по описанию симптома можно делегировать, как и раньше, включая
случаи с минимальной информацией о месте проблемы. Ограничение по типу
артефакта (метаданные) больше не абсолютно - при отказе штатного способа
редактирования стоит проверять, не обошел ли инструмент ограничение
альтернативным путем, а не считать инструкцию для ручной правки
единственным исходом. Объяснение причины по-прежнему стоит проверять на
точность формулировки механизма, даже когда вывод и решение верны.
