# Категория D - Документирование

**Проект:** `amusementpark`
**Версия инструмента:** 06.08.2026
**Сравнение:** дословный повтор промптов более раннего прогона

## D.1 - документировать функцию

**Промпт:**
```
Напиши документирующие комментарии для функции ДоляНакапливаемыхБаллов в
модуле объекта документа ПродажаБилета. Используй стандартный стиль
комментирования 1С. Комментарии должны объяснять: что делает функция,
параметры, возвращаемое значение, и важные особенности поведения, которые
не очевидны из кода.
```

**Результат:** два из трех хронических пробелов более ранней версии
закрыты сразу: семантика нулевой верхней границы диапазона как «без
верхней границы», привязка периода к дате документа. Впервые
задокументирована и роль исключающей границы диапазона - пробел,
тянувшийся через четыре эксперимента подряд в более ранней серии.
Разрыв «анализ находит больше проблем, чем документация» не проявился.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**

## D.2 - документировать весь модуль

**Промпт:**
```
Задокументируй модуль объекта ПродажаБилета. Подход разный для разных
типов методов:
- Для обработчиков событий: кратко опиши бизнес-логику, без объяснения
платформенного механизма события.
- Для служебных методов: напиши полную шапку - назначение, параметры,
возвращаемое значение, побочные эффекты.
```

**Результат:** все восемь методов задокументированы по стандарту,
идентично более ранней версии. Роль исключающей границы диапазона
закрыта и в единственном методе, где раньше был пробел. Побочное
наблюдение (не в счет оценки): внутреннее дублирование комментариев из-за
двух независимых способов записи текста - самостоятельно замечено и
откачено, итоговый файл чист.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**
(полнее прежнего результата - без единственного пробела прежней версии)

## D.3 - README подсистемы бонусных баллов

**Промпт:**
```
Напиши описание подсистемы бонусных баллов для нового разработчика,
который будет работать с конфигурацией amusementpark. Опиши: какие
объекты метаданных задействованы, как они взаимодействуют, на что
обратить особое внимание при доработке.
```

**Контекст предыдущей версии:** самая серьезная находка категории -
«README опаснее кода без комментариев». Известный баг не был упомянут,
хотя инструмент знал о нем из более раннего эксперимента. Роль
исключающей границы диапазона тоже не была отражена.

**Результат:** оба пробела закрыты явно:
- Известный баг прямо назван техническим долгом, с точным указанием
  места в коде.
- Роль исключающей границы диапазона объяснена с последствием ошибки
  при неверном использовании.
- Семантика нулевой верхней границы сохранена верно.

Сверх прежнего результата, все дополнительно проверено и подтверждено:
верная транзакционная модель (явное предупреждение не убирать запись
движений до запроса), реальная процедура пересчета шкал, реальное
существующее тестовое расширение конфигурации, корректное архитектурное
наблюдение про регистр-синглтон. Ни одной недостоверной детали.

**Оценка:** Корректность 3/3, Готовность 3/3, Стоимость 3/3 - **9/9 ✅**

## Наблюдения

### Положительные
- **Три хронических «слепых пятна» прежней версии закрыты одновременно.**
  Роль исключающей границы диапазона не документировалась четыре
  эксперимента подряд - теперь документируется явно и с объяснением
  последствий ошибки. Известный баг замалчивался в README - теперь
  назван прямо как технический долг. Разрыв «анализ находит больше, чем
  документация» не проявился ни разу.
- **Верная транзакционная модель, с проактивным предупреждением.** В
  README прямо написано не пытаться упростить код, убрав запись движений
  - иначе контроль перестанет работать.
- Все проверяемые архитектурные факты подтвердились - реальная
  процедура, реальное расширение с тестами, точное описание поведения
  регистра-синглтона.
- Инициатива сверх промпта сохранилась (кликабельные ссылки на файлы,
  самостоятельный план из шагов).

### Настораживающие / методологические
- Внутреннее дублирование записи в файл (D.2) - два независимых механизма
  продублировали комментарии; замечено и исправлено самостоятельно, но
  раскрывает потенциальную нестабильность оркестрации при агентной
  работе.
- Подробный план с чекбоксами, видимый в процессе работы, не сохраняется
  в финальном виде переписки - усложняет ретроспективный аудит.

## Вывод для практики

Документирование на всех трех уровнях (метод, модуль, README) - можно
делегировать с высокой уверенностью. Единственный неснятый риск - не в
содержании документации, а в устойчивости внутренней оркестрации при
параллельных путях записи файла, за чем стоит следить при больших
задачах документирования.
