# Категория A - Генерация кода по техническому заданию

**Проект:** `amusementpark`
**Версия инструмента:** 06.08.2026
**Сравнение:** с прогоном той же формы задачи на более ранней версии
(до обновления с редактированием метаданных)

## Задача

Структурный аналог более раннего эксперимента - та же форма задачи
(функция → структура с полями шапки, подсчетом строк табличной части и
булевым флагом), но на другом документе, чтобы исключить эффект «уже
видел такой ответ» и проверить сохранность паттернов, а не запомненный
текст.

Написать функцию на BSL, которая принимает ссылку на документ
`ВозвратБилета` и возвращает структуру:
- `Клиент` - наименование клиента
- `СуммаДокумента` - итоговая сумма из шапки
- `КоличествоПозиций` - количество строк в табличной части
  `ПозицииВозврата`
- `ЕстьКрупныйВозврат` - Булево, Истина если `СуммаДокумента > 10000`

При пустой ссылке - вернуть структуру с пустыми значениями.

## Контекст конфигурации (передан в промпте)

| Объект | Реквизиты |
|---|---|
| Документ `ВозвратБилета` | Основание, Клиент (ссылка на справочник «Клиенты»), СуммаДокумента (Число), Комментарий, Ответственный, Филиал |
| Табличная часть `ПозицииВозврата` | Номенклатура, Цена, Количество, Сумма |

## Ход эксперимента

### Итерация 1 - первый промпт, без подсказок решения

**Промпт:**
```
Документ ВозвратБилета содержит реквизиты шапки: Основание (ссылка на
документ ПродажаБилета), Клиент (ссылка на справочник Клиенты),
СуммаДокумента (Число), Комментарий, Ответственный, Филиал.
Табличная часть ПозицииВозврата содержит реквизиты: Номенклатура, Цена,
Количество, Сумма.

Написать функцию на BSL, которая принимает ссылку на документ ВозвратБилета
и возвращает структуру:
- Клиент - наименование клиента
- СуммаДокумента - итоговая сумма из шапки
- КоличествоПозиций - количество строк в ТЧ ПозицииВозврата
- ЕстьКрупныйВозврат - Булево, Истина если СуммаДокумента > 10000

При пустой ссылке - вернуть структуру с пустыми значениями.
```

**Результат:** Напарник сразу выбрал путь через запрос к базе, минуя
промежуточное получение объекта документа. Порог `10000` вынесен в
именованную переменную. Проверка на пустую ссылку - до формирования
запроса.

Но в запросе использован скалярный коррелированный подзапрос прямо в
списке `ВЫБРАТЬ` - конструкция, привычная по обычному SQL, но не
поддерживаемая языком запросов 1С. При реальном запуске платформа выдала
синтаксическую ошибку. Проверка по всей конфигурации подтвердила: такой
паттерн («подзапрос в списке ВЫБРАТЬ») нигде в проекте не встречается -
только как производная таблица в `ИЗ (...)` или в условии `ГДЕ ... В
(...)`.

Напарник заявил, что «проверит синтаксис», и исправил два стилистических
замечания (алиас у `КОЛИЧЕСТВО(*)`, магическое число) - то есть
заявленная самопроверка поймала косметику, но не поймала фатальную
ошибку запроса.

### Итерация 2 - передан текст реальной ошибки, без подсказки причины

**Промпт:**
```
При выполнении функции возникает ошибка:

Ошибка при вызове метода контекста (Выполнить)
Выборка = Запрос.Выполнить().Выбрать();

[ОшибкаВоВремяВыполненияВстроенногоЯзыка]
по причине:
{(4, 3)}: Синтаксическая ошибка "ВЫБРАТЬ"
(<<?>>)ВЫБРАТЬ

Почему возникает ошибка и как исправить запрос?
```

**Результат:** запрос переписан через `ЛЕВОЕ СОЕДИНЕНИЕ` +
`СГРУППИРОВАТЬ ПО`, с верным полем для подсчета строк (номер строки, а не
предметное поле - характерная ошибка агрегатной функции, встречавшаяся в
более ранней версии, здесь не повторилась).

Но объяснение причины исходной ошибки оказалось фактически неверным:
«подзапрос в списке выборки поддерживается не всеми версиями платформы
1С». Это не так - это категориальное ограничение языка запросов, не
вопрос версии. Проверка в среде разработки не выявила проблем в
исправленном коде - но, как показала следующая итерация, это было ложное
чувство завершенности: статическая проверка модуля не разбирает текст
запроса внутри строкового литерала на семантические ошибки.

### Итерация 3 - новая ошибка при реальном запуске, снова без подсказки

**Промпт:**
```
При выполнении запроса снова ошибка:

Ошибка при вызове метода контекста (Выполнить)
Выборка = Запрос.Выполнить().Выбрать();

[ОшибкаВоВремяВыполненияВстроенногоЯзыка]
по причине:
{(8, 6)}: Неоднозначное поле "ПозицииВозврата.Ссылка"
ПО ПозицииВозврата.Ссылка = ВозвратБилета.Ссылка

Почему возникает ошибка и как исправить запрос?
```

**Результат:** алиасы таблиц переименованы (совпадение алиаса шапки
документа с именем типа объекта в составном пути табличной части убрано)
- правильное, стандартное решение для этого класса ошибок.

Объяснение причины снова отчасти неточное: «в некоторых сборках
платформы такой алиас перекрывает имя объекта» - вновь версия-зависимая
формулировка там, где действует общее правило языка запросов
(совпадение алиаса с именем объекта метаданных - известный антипаттерн
независимо от сборки).

Запрос выполнен без ошибок - подтверждено реальным запуском в
1С:Предприятии.

## Итоговая оценка

| Критерий | Балл | Обоснование |
|----------|------|-------------|
| Корректность | 3/3 | Финальный запрос подтвержден реальным запуском без ошибок |
| Готовность | 2/3 | Финальный код рабочий, но получен как фрагмент - требует небольшой интеграции в функцию |
| Стоимость получения | 2/3 | 3 итерации, из них 2 - исправление кода, который вообще не выполнялся |
| **Итого** | **7/9** | ✅ с оговоркой (см. ниже) |

**Оговорка к вердикту.** Формальная сумма дает положительный вердикт по
методике - это взвешено честно: ось «корректность» отражает финальный
результат, а не путь к нему, путь отражен отдельно в оси «стоимость». Но
качественная картина ближе к среднему, а не к безоговорочно хорошему
результату: рабочий вариант удалось получить только через три прогона,
два из которых - не стилистические доработки, а исправление кода,
который вообще не выполнялся. Разработчик без экспертизы в специфике
языка запросов 1С мог бы застрять на любой из двух ошибок.

## Наблюдения

### Положительные
- Ошибка выбора поля для агрегатной функции из более ранней версии не
  повторилась.
- Путь к решению выбран сразу через запрос, без избыточных
  промежуточных конструкций.
- По одному лишь тексту реальной ошибки платформы, без единой подсказки
  причины, направление исправления определено верно дважды подряд.
- Порог вынесен в именованную переменную - аккуратная практика.

### Настораживающие
- **Новый, более тяжелый класс дефекта.** Раньше встречались тихие
  семантические баги - код работал, но неверно. Здесь дважды подряд код
  вообще не выполнялся.
- **Уверенно неверные объяснения причины - дважды подряд, один и тот же
  тип ошибки.** Оба раза категориальное правило языка запросов объяснено
  через версию или сборку платформы, хотя оба ограничения - общие
  свойства языка запросов, не зависящие от версии.
- **Проверка в среде разработки после исправления дала ложное чувство
  завершенности** - статический анализ не разбирает текст запроса внутри
  строкового литерала на семантические ошибки. Только реальный запуск
  вскрыл вторую ошибку.

## Вывод для практики

Задачу стоит формулировать с полным описанием реквизитов в промпте.
Обязательное условие делегирования - ревью через **реальный запуск**, не
только через статическую проверку в среде разработки. Объяснениям причин
ошибок, особенно со ссылкой на версии или сборки платформы, доверять
буквально не стоит - их полезно перепроверять по документации языка
запросов отдельно.

## Дополнительно: усвоение письменных правил оформления кода (июнь 2026)

Отдельная, более ранняя проверка (до появления версий с редактированием
метаданных) выясняла, при каких условиях инструмент действительно
применяет письменное правило оформления, данное только текстом, без
примера кода. Повод: в одном из экспериментов категории тестирования
правило про обязательное явное управление транзакцией при регистрации
тестов, данное только текстом, было проигнорировано дважды подряд, а то
же правило с примером кода «плохо/хорошо» - выполнено сразу. Возникла
гипотеза, что дело в природе правила: простые локальные вставки в код
усваиваются из текста, а правила-«обрамления» требуют примера.

Проверка на трех новых правилах того же формального класса - обязательное
ключевое слово для неизменяемых параметров функции, обязательный формат
комментария-справки к функции, и явное управление транзакцией при записи
в регистр (правило того же типа «обрамления», что и в тестах, но не то же
самое правило) - дала неожиданный результат: **все три правила выполнены
верно текстом, без единого примера**, включая правило-обрамление,
структурно аналогичное провалившемуся.

**Пересмотр вывода.** Правило про транзакцию в тестах, скорее всего,
провалилось не потому, что было «обрамлением», а потому что отсылало к
особенностям конкретного тестового фреймворка, с которым инструмент был
знаком неточно (в том эксперименте были зафиксированы несколько
подряд неверно воспроизведенных вызовов именно этого фреймворка). Пример
кода в тот раз сработал не как «наглядность правила», а как единственный
надежный источник правильного синтаксиса незнакомого API. Практический
вывод: правила, использующие штатные конструкции языка и платформы,
можно формулировать текстом без примера; пример становится по-настоящему
нужен именно там, где правило отсылает к менее известному API стороннего
фреймворка или расширения.

**Побочные наблюдения той же проверки:**
- Ключевое слово для неизменяемого параметра не подставляется по
  умолчанию туда, где оно уместно, если правило не сформулировано явно -
  стилевые предпочтения нужно называть, а не рассчитывать, что инструмент
  «дорастит» стиль сам.
- Несуществующий реквизит не был выдуман - вместо этого выполнен поиск по
  составу метаданных, констатация отсутствия и разумная переинтерпретация
  задачи через реально существующие данные.
- При задаче записи в объект без указания целевого модуля и с несуществующим
  объектом в условии - вместо выдумки инструмент ушел в исчерпывающий обход
  всех модулей конфигурации и не завершился за разумное время. Это
  зеркальная сторона риска «уверенно выдумывает»: вместо ошибочного
  результата - непродуктивная трата времени вместо прямого вопроса
  человеку. Задача решилась после того, как формулировка была уточнена
  явным запретом полного обхода конфигурации.
